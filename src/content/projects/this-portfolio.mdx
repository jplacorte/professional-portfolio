## The problem

A portfolio has two audiences with opposite needs. Recruiters skim: they want to know in ten seconds what I do and whether it’s worth a call. Engineering managers dig: they want to see how I think about trade-offs. The site had to serve both without becoming either a flashy demo reel or a wall of text.

It also had to be evidence in itself. A slow, janky portfolio from someone who claims to care about performance undermines every other claim on it.

## Constraints

- **Performance budget:** 95+ Lighthouse on every page, including the animated ones.
- **Zero-ops:** no database or CMS to keep alive for a site that changes a few times a month.
- **Accessible motion:** every animation must degrade to a calm, static page under `prefers-reduced-motion`.
- **Secure by default:** a strict Content Security Policy and hardening headers on every response.
- **Cheap:** runs on free tiers indefinitely.

## Architecture

<SiteArchitecture />

Every page is pre-rendered at build time and served from the CDN. The only code that runs on a server is `/api/contact`, marked `prerender = false`, which verifies a Cloudflare Turnstile token and sends mail through Resend.

Content lives in the repo as MDX, validated by a Zod schema at build time. A case study with a missing `role` or a malformed link fails the build rather than shipping a broken page:

```ts
const projects = defineCollection({
  loader: glob({ pattern: '**/*.{md,mdx}', base: './src/content/projects' }),
  schema: z.object({
    title: z.string(),
    summary: z.string().max(180),
    role: z.string(),
    stack: z.array(z.string()).min(1),
    status: z.enum(['live', 'complete', 'in-progress', 'archived']),
    draft: z.boolean().default(false),
    // …
  }),
});
```

## Key decisions

**Astro over Next.js.** Next.js is my day-to-day framework, and the obvious choice would have been to use it. But this is a content site with a handful of interactive islands; Astro ships zero JavaScript by default and lets me opt in per component. The result is a faster site with less to maintain — the same “right tool, not favourite tool” call I make on client projects.

**Git-based content over a headless CMS.** I’m the only author. A CMS would add a service, a bill and an auth surface in exchange for an editing UI I don’t need. MDX in Git gives me versioning, pull-request previews and schema validation for free.

**Native browser APIs over an animation library.** Scroll reveals use CSS scroll-driven animations (with an `IntersectionObserver` fallback), the hero is a hand-written canvas loop with its physics in pure, unit-tested functions, and page transitions use the browser’s cross-document View Transitions. That keeps the motion layer to a few kilobytes and lets the browser run most of it off the main thread.

**Native page transitions over a client router, because of the CSP.** The first version used Astro’s `<ClientRouter />` for the title morph between pages. When I added a hash-based Content Security Policy, a browser test caught that the router’s generated styles and scripts were blocked, and Astro documents the two as incompatible. The options were to weaken the policy with `'unsafe-inline'` or to drop the router. I dropped it: native cross-document View Transitions give the same morph in Chrome, Edge and Safari, ship no router JavaScript, and every page becomes a real page load, which removed a class of re-initialisation bugs. Browsers without support simply navigate normally.

**Motion as progressive enhancement.** All animation CSS sits inside `@media (prefers-reduced-motion: no-preference)`. The canvas renders a single static frame for reduced-motion users and pauses whenever it scrolls off-screen or the tab is hidden, so it never burns battery in the background.

## Security

- **Content Security Policy** generated by Astro: every script and stylesheet is allowed by its SHA-256 hash, so `script-src` has no `'unsafe-inline'`. The one hand-written inline script (applying the saved theme before first paint) is hashed from the same constant it is rendered from, so the two can never drift.
- **Hardening headers** on every response (HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`), added to Vercel’s build output by a small, unit-tested Astro integration.
- **Contact endpoint**: same-origin check against CSRF, body-size and content-type limits, schema validation that strips line breaks from anything that reaches an email subject, a honeypot, Turnstile verification that fails closed, and timeouts on every outbound call.
- **Supply chain**: `npm audit` is clean and gated in CI, with Dependabot and weekly CodeQL scanning. The patched release of one transitive dependency broke how the OG-image renderer read fonts. A pixel comparison caught it, so instead of pinning the vulnerable version I unpack the fonts with Node’s built-in zlib, which leaves that code path unused.

## Delivery pipeline

Every pull request runs a dependency audit, ESLint with type-aware rules, Prettier, `astro check`, Vitest unit tests and a production build. In parallel it then runs Playwright end-to-end tests on desktop and mobile against the built site, served with the real CSP and headers: page smoke tests, navigation, the theme toggle, the contact form, a CSP-injection check and axe WCAG 2.1 AA scans of every page in both themes. Lighthouse CI enforces 95+ in every category, and a link checker validates the generated HTML. Vercel posts a preview URL on the PR; merging to `main` deploys.

Architecture decisions are recorded as ADRs in `docs/adr`, so the reasoning lives next to the code it explains.

## What I’d do differently

Hosting is the open question. Vercel’s platform-level bot mitigation blocks Meta’s link-preview crawler on free plans, so links shared on Facebook and Messenger show no preview. Everything else works, and LinkedIn, where recruiters actually click, renders the full card. If those previews start to matter, I’d move hosting to Cloudflare. The static-first architecture makes that a small change: swap the adapter, port one function, and keep the same headers.
